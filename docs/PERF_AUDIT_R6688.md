## 2. Находки и возможности (по убыванию эффекта)

### PF-1 (P2): прямые посетители игры не получают Service Worker → повторный визит снова качает ~21–38 МиБ

- `game/index.html` НЕ содержит `navigator.serviceWorker.register` — регистрация
  живёт только в `js/main.js` (лендинг). SW-маршруты `/game/assets/` +
  `/game/vendor/` (cache-first, бакет game-assets-v45) в `sw.js` полностью
  готовы, но активируются лишь если игрок сначала открыл лендинг.
- Живой замер (Playwright, 1280×800): игра, визит 1 — 1407 запросов / 38.5 МиБ;
  визит 2 — **снова 1407 запросов / 38.5 МиБ** (SW=none). Лендинг в том же
  прогоне: визит 2 — **1099 мс против 10 596 мс** (SW=active) — SW работает и
  даёт ~10× на повторных визитах.
- Доля прямых входов в игру (поисковики, шаринг ссылки /game/) не получает
  ничего из этого выигрыша.
- **Рекомендация**: одна строка в `game/index.html` —
  `navigator.serviceWorker.register('/sw.js')` (SW скоуп `/`, маршруты уже
  готовы) + бамп SW по §4.3. Эффект: повторный визит игры — из кэша
  (миллионы байт трафика и десятки секунд на 4G).

### PF-2 (P2): мобильный LCP лендинга ~5.0 с — hero-изображение 1920px без srcset

- `assets/images/title.webp` — 1920×1097, **188 КиБ**, отдаётся мобильному
  вьюпорту 412px как есть (`<picture><source srcset="assets/images/title.webp">`
  без `sizes`/промежуточных ширин; `fetchpriority="high"` и width/height — целы).
- Lighthouse image-delivery-insight: потенциальная экономия **180 КиБ** (~95%)
  на мобильном LCP-элементе; cache-insight добавляет сюда же 173 КиБ (TTL 600 c).
- **Рекомендация**: сгенерировать title-800/1280/1920.webp и подключить
  `srcset="… 800w, … 1280w, … 1920w" sizes="100vw"` (+EN). Ожидаемый LCP
  mobile: −1.5…−2 с (4G). Артефакт не тронут — на согласовании владельца.

### PF-3 (P3): TTL кэша GitHub Pages 600 с — компенсируется SW, но не для игры (см. PF-1)

- cache-insight лендинга: 311 КиБ (title.webp 173 + styles.css 14 + js-модули);
  игры: 1132 КиБ (phaser.min.js 287, i18n.js 108, InteriorScene 73, dialogue.js 52…).
- Заголовки GitHub Pages (`max-age=600`) владелец изменить не может. Лендинг
  закрыт SW (network-first + офлайн-копия + cache-first ассетов), игра — нет
  (PF-1). Починка PF-1 закрывает и это.

### PF-4 (P3): длинная задача reveal.js 234 мс + Metrika 131 мс на мобильном

- TBT лендинга 205–351 мс — в целом хорошо; основной вклад —
  `js/modules/reveal.js` ( IntersectionObserver-раскрытие карточек) и
  `mc.yandex.ru/metrika/tag.js` (94 КиБ, unused-js 50 КиБ — сторонняя аналитика).
- **Рекомендация** (не срочно): в reveal.js — батчить первичное раскрытие
  через requestIdleCallback/`requestPostFrame`; Metrika уже подключена с
  `defer` — оставить как есть.

### PF-5 (P4, косметика): unminified-css 6 КиБ / unminified-js 2 КиБ

- styles.css и модули отдаются без минификации (экономия мала — GitHub Pages
  gz-жмёт: CSS 16→4 КиБ по сети). Можно принять как стиль проекта
  («читаемый исходник»); минификация даст ≤6 КиБ/страницу.

### Принято без изменений (обосновано)

- **BP 77 у лендингов** — целиком из-за сторонних cookies/консоли Яндекс.Метрики
  в лабораторной песочнице (fetch к `mc.yandex.ru/watch` в песочнице →
  ERR_FAILED; у реальных пользователей запрос валиден). Проверено повторными
  прогонами: сайт-собственные скрипты консоль не засоряют.
- **CLS = 0** на всех трёх страницах — инварианты width/height img и
  шрифтовых резервов работают.
- **Вес лендинга 441 КиБ** — отличный (из них 189 hero + 94 Metrika).

## 3. Итог

Сайт технически здоров (A11y/SEO 100, CLS 0, desktop 96). Два структурных
резерва — PF-1 (SW для игры, ~одна строка + бамп) и PF-2 (srcset для hero,
−180 КиБ mobile LCP) — дают наибольший эффект на реальных мобильных
пользователей; оба не ломают пинов тестов и могут быть исполнены одной
итерацией по приказу владельца.
